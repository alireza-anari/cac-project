# S0-09C experimental recovery fence design

Status NEW_IMPLEMENTATION_EXPERIMENTAL / PROTOCOL_PROPOSED. Spec: Issue #19 and
main/docs/architecture/S0_09B_ARCHITECTURE_RULING.md. User explicitly delegates
architecture and independent execution. Parent 75be54d0f18d6391014ca4e5d91466d62a6cf72c.
No merge, product identity, public API, business writes, production keys or TTL approval.

## Candidates and choice

1. External fsync append-only file/SQLite CAS coordinator: outside app dump, simple
single-host durability. Correct cross-process lock lifetime, anti-rollback and
remote/network behavior require another service protocol and transport proof.
2. Independent PostgreSQL authority: a third PostgreSQL cluster with WAL-backed
monotonic bigint epoch, serialized CAS reserve/confirm and live transaction locks.
Chosen for observable locking, independent crash/restart, role ACLs and real SQL
fault injection. This is a synthetic single-authority experiment, not consensus
or HA. Its own backup rollback/Byzantine compromise and common host loss remain P0.

## Topology and authority identity

Three independently initialized containers/clusters: original A, restored B,
anchor C. Distinct pg_control_system system identifiers and PGDATA witnesses.
Only application schemas are dumped A->B; no anchor state is in that artifact.
Anchor state owns epoch/generation/phase/owner/request ID. Immutable instance
registration binds per-instance anchor SQL login, independent cluster system ID
and synthetic MAC secret. App guard derives actual cluster ID from pg_catalog;
a copied old app config cannot impersonate the old cluster after logical restore.
This does not work as physical-PITR identity attestation; physical PITR is untested.

## Activation state machine

EMPTY -> RESERVED(epoch+1, candidate, request UUID, fresh generation UUID)
-> local generation/state durable apply (not ready) -> ACTIVE -> local ready.
Reserve uses expected epoch CAS, rejects competing/duplicate allocation, and
makes all old authority unavailable immediately. Same request retry returns the
same reservation without another epoch. A newer reservation fences a previous
pending candidate too. Confirm requires a MACed local DB acknowledgement of the
committed instance/epoch/generation/system ID. Reconfirm is idempotent only for
that same current activation. Ready is checked online; no local-only fallback.
Crash before reserve leaves old active. Crash after reserve is safe downtime;
resume current request from the independent anchor, never from restored state.
Every later phase may be retried; partial failure never re-enables an old epoch.

## Online operation gate and SQL enforcement

Trusted broker prepares an operation ticket at C, bound to instance, epoch,
actual local PID/xid/system ID and the specific anchor backend. It then takes
FOR SHARE on C's singleton state and a transaction advisory lock for that ticket.
While that lock is held it performs local SQL and detached issuer COMMIT; only
then releases the anchor transaction. Reserve's UPDATE cannot overlap that gate.
Readiness alone is not authority and no cached lease permits offline operation.

A new reversible migration wraps poc.challenge/issue/verify; original bodies are
renamed guard-private and their role grants removed. Existing SQL source files
and 94 cases remain byte-for-byte unchanged; their suites run without the new
experimental migration. Wrapped APIs demand a transaction-local operation ticket
and independently contact C through dblink on every call, including RLS verify.
C checks active ownership, PID/xid/system ID, ticket digest and live granted
advisory lock. Its response is MACed and bound to a fresh DB-generated nonce;
cached/stale response replay fails. Credentials/secret stay in guard-owned tables.
Old direct API SQL with no ticket is denied. Restoring a ready flag or old row
cannot recreate a live anchor lock or the registered physical cluster identity.

Linearization is the guarded operation, not wall-clock response delivery.
Already authorized in-flight responses may arrive after an activation response;
activation cannot commit until prior guarded DB transactions have committed or
aborted. No retroactive deletion of returned reads is claimed. Anchor restart
kills guard sessions; DB-side rechecks fail closed, and every broker revalidates
before returning. Lost connection/timeout means no returned token/read, though a
local commit may have happened; replay uses the independently committed ledger.

## Proof obligations and crash matrix

Tests include reserve/apply/confirm/ready/first-issue process crash checkpoints;
duplicate activation/lost response; real A/B concurrent operations and takeover;
long transactions, savepoints/rollback and reused connection; actual anchor
stop/restart and wrong endpoint; stale signed response, stale epoch CAS and
copied ready/config; incorrect/missing roles/ACL/extension/bootstrap; actual
independent-cluster logical restore. Negative controls bypass the fence to
reproduce S0-09B unsafe response, disable CAS and admit duplicate ownership.
Every control restored exactly in finally; structural down/up and suites rerun.
No manual generation-row update counts as a fencing proof.

## Limits and decisions still proposed

Trusted: test admin, DB guard, issuer/broker, C's durable non-rollbacked storage,
host kernel and network endpoints. No malicious administrator, Byzantine anchor,
quorum, external KMS, TLS deployment, physical restore, production HA/RPO/RTO,
real identity or approved HMAC/canonical bytes. A third container on one CI host
is an independent DB/restore failure domain, not an independent physical site.
Per-operation gate gives safety at cost of availability and lock contention.
Default timeouts are test inputs; anchor outage permits no offline cache.

## Builder-review correction: durable unresolved operations

A live anchor lock alone was rejected: C restart releases locks while local SQL
may continue. Before any gate can authorize, its OPEN operation intent is
committed to C's WAL. Reserve also refuses any OPEN intent, even if every live
lock vanished. Broker closes an intent only after confirmed local COMMIT or
ROLLBACK and online anchor postvalidation. Ambiguous local outcome, broker death
or lost anchor session leaves OPEN durable; no timeout may silently close it.
Anchor prepare rejects orphan OPEN sessions (PID + backend_start binding).
This deliberately causes fail-closed downtime after ambiguous crash. Automatic
resolution of uncertain outcomes is NOT implemented; trusted administrative
resolution would require independent proof that old local transactions cannot
still commit. Tests reset fixtures only AFTER asserting the blocked state;
fixture resets must never be presented as an operational recovery protocol.

Runtime session gates last through the entire outer local transaction, including
challenge/use; detached issuer operations have separate gates. App wrappers
check before and after the original SQL body; broker postchecks protect returned
results too. Late delivery of an operation authorized before a failure is allowed;
no new owner can activate while its durable OPEN intent is unresolved.

A MAC from the apply transaction alone does not prove commit. DB activation ACK
must read applied state through an independent loopback dblink connection and
require the requested epoch/request/generation to be visible there. An uncommitted
apply or rolled-back apply cannot produce a confirming ACK. Loopback reader has
only a narrow committed-state accessor, not general table/key access.
