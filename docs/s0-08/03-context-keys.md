# Trusted issuer, signed context and key lifecycle

**PROPOSED — ADR-08-02 / CR-08-02. Current PR #11 format is unchanged.** Its HMAC verifier uses seven fields, one private key, tx/PID binding and a 300-second maximum. It lacks the proposed audience/version/key lifecycle and authoritative epoch checks. Never send a v2 token to v1 and infer equivalent protection.

## Authority and issuance

Recommend an isolated issuer with no browser-facing generic “sign JSON” endpoint. A web worker presents an authenticated workload identity, opaque server session proof, requested action/target/scope and a database challenge. Issuer independently loads authoritative active session/principal, verified status, MFA evidence and current delegation; it derives actor and allowed scope. It must not trust the worker's claimed principal, MFA time, tenant ownership, role or capability list. Authentication of the workload is necessary but not sufficient. Unauthorized/unavailable identity evidence yields no token. Issuer has no general tenant business-write privilege.

Challenge proposal: a narrow DB function returns DB-generated transaction id, backend PID, random transaction nonce and installation generation without reading tenant data. The authenticated issuer service receives the challenge and verifies its server provenance (recommended: a challenge signature under a distinct DB-to-issuer HMAC key, approved through D-03). Caller-supplied tx/PID alone is insufficient proof of workload/DB identity. The challenge signature binds nonce, tx, PID, actual login, DB generation, audience and a short expiry; the issuer verifies it with the separate challenge-verification key. The context verifier rechecks the embedded challenge signature and live tx/PID/generation. Do not reuse the context-signing key for challenge signing. A protected transaction-binding registry, writable only by the installer/action gate, records the accepted actor/session/scope/nonce for `(generation, tx, pid)` and refuses conflicting replacement while its row exists; bounded expiry cleanup removes committed metadata, never secrets. Rollback removes uncommitted bindings; this table alone cannot resist savepoint rollback by arbitrary SQL. Therefore the issuer also atomically records the first issuance tuple `(generation, tx, pid, actor, session, scope, action, digest, nonce)` in a protected issuance ledger committed independently of the caller transaction. A second challenge for that transaction cannot change the tuple or extend expiry. Identical retransmission still requires current authorization and can return only the original unexpired envelope. The DB challenge includes signed transaction-start time (from DB transaction timestamp); issuer accepts it only within a proposed 5-second issuance window. Ledger retention at least 120 seconds after that start exceeds issuance window, maximum token lifetime and clock allowance; later challenges for the same old transaction fail age checks even after ledger purge. Fail closed if ledger unavailable. This separate atomic ledger/window is essential to the proposal; transactional DB metadata alone is not an anti-switch proof. This is a proposed new DB object/privileged interface, not a property of an ordinary GUC. Repeated statements use the same binding; fresh transaction gets a fresh one. The verifier compares challenge fields to the *actual* current transaction/connection and private installation generation. A transaction holds its server connection while issuance happens; a 2-second issuer deadline and 5-second transaction budget are initial proposals. No retry extends the same token lifetime. Identity read/challenge functions are an explicit pre-context allowlist, not a general data query escape hatch.

## Proposed v2 envelope

Fixed algorithm allowlist (initial HMAC-SHA256), explicit `v=2`, `kid`, exact `iss` and installation-specific `aud`; no algorithm negotiation from the caller, key URL fetching, fallback kid or unknown-version acceptance. Sign an unambiguous versioned canonical byte encoding; test duplicate JSON keys, numeric coercions and alternate encodings. Proposed strict JSON types below; no raw credential/PII in claims. Limit envelope size to 4096 bytes and reject unknown mandatory fields/unsupported versions. Version-specific extension policy must be defined before adding fields.

| Claim | Source and binding |
|---|---|
| `principal`, `session_ref`, `principal_epoch`, `session_epoch` | Immutable actor and opaque session reference from authoritative identity service; integer epochs, active-state recheck in DB |
| `tenant`, `store`, `authz_epoch` | UUID scope resolved and authorized server-side; one Store per transaction; Store epoch checked under guard |
| `action`, `target`, `request_digest`, `idempotency_ref` | Exact operation, target principal/object and canonical normalized body digest; read context has no mutation authority |
| `purpose`, `db_login` | Separate runtime/read, bootstrap and onboarding operation purposes; actual session_user must match permitted login |
| `iat`, `exp`, `mfa_ref` | Integer UTC epoch seconds; trusted MFA evidence reference checked for sensitive actions; never a browser assertion |
| `tx`, `pid`, `nonce`, `db_generation` | Actual DB challenge values, strict tx string/PID integer; nonce tied to current transaction; generation changes after restore/failover |
| `v`, `kid`, `iss`, `aud` | Protected protocol/key routing and exact installation/environment binding |

Recommend issuance TTL <=60 seconds, `exp <= iat+60`, `exp > current DB statement time`, iat no more than 5 seconds ahead, no grace after expiry. Current 300-second verifier ceiling is not silently reused; this is a security-contract diff. Clock drift beyond tolerance disables issuance/alerts; do not widen validity automatically. Timeout must stop long statements/transactions; expiry cannot retract rows from an already executing statement.

Verifier authenticates bytes then checks types, every binding, active key/session/principal/Store epochs and action authorization. Read RLS uses verified actor/scope and current capability, not signed claim alone. Mutation gateway compares action/target/body digest to actual arguments before effects. Context is never re-signed after changing actor/target/scope within a transaction. Token copied to another transaction, connection, installation, login purpose, request or session fails. Repeated calls within one transaction are not magically prevented by a nonce: idempotency record and command consumption enforce at most one effective mutation for the request.

## Key storage, lifecycle and incident response

Recommended experimental direction: isolated broker holds signing material; restricted verifier storage holds matching HMAC verification material (HMAC verifiers can also mint signatures). DB admin and issuer are therefore trusted. Encrypt at rest using a separately controlled deployment secret; app roles cannot read key rows or unwrap keys; no repo/env dumps/artifacts/logs. Real infrastructure, provider and encryption implementation remain unselected. An asymmetric alternative reduces verifier minting power but needs a reviewed PostgreSQL verifier/extension; remote KMS calls inside RLS are not an acceptable implicit substitution.

Proposed key registry fields: kid, algorithm/version, environment/audience, not_before/not_after, state, created/activated/revoked metadata and protected verification material. State transitions: staged -> active_signing -> verify_only -> retired; any state -> revoked. Unique active signer per environment/version; trusted operators only. Stage verifier key first, then atomically activate broker kid; verify-only overlap no longer than maximum token lifetime plus bounded deployment/clock allowance (propose 65 seconds after last issuance). Retire only after outstanding transactions expire/finish. Unknown/not-yet-valid/retired/revoked kid fails; outage never falls back to an old key.

Revocation is an online authoritative check, not just deleting broker material. Emergency compromise: stop issuance, revoke kid/generation, block new operations, terminate affected in-flight connections where needed, rotate keys, invalidate affected sessions, review audit and restore from a trusted configuration. Already committed effects need incident reconciliation; signing revocation is not a database rollback. Restart/restore may revive old epoch/key rows, so generation must be refreshed outside the restored snapshot before access resumes. Fail closed if durable generation or key registry cannot be authenticated.

Log only key id, opaque request/decision id, scope identifiers permitted by retention policy, result class and reason code. Never log token, signature, key, session cookie or invite secret. SQL parameter/error logging, proxy access logs, APM and outbox export are part of acceptance testing. Rotation/issuance/denial events are append-only security records; DB business audit is separate. Signing success is not business-operation success.
