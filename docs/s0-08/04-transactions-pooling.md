# Database transaction, roles and connection-pooling contract

**PROPOSED — ADR-08-03 / CR-08-03.** No current role grants or migrations changed.

## Role and interface matrix

| Role boundary | Allowed | Forbidden |
|---|---|---|
| runtime login | Scoped SELECT after verified read context; execute only named challenge/authorization interfaces | Domain DML, DDL, TRUNCATE, key reads, SET ROLE to privileged roles |
| bootstrap provisioner login | Explicit first-store command only, actor-bound enrollment/idempotency | Generic cross-principal membership/grant INSERT |
| onboarding service login (new proposal) | Execute named invite/accept/revoke commands with signed actor/action/target | Direct table writes or unrestricted provisioning; no caller-selected function names |
| identity adapter login (new) | Narrow authenticate/revoke/session-state interfaces | Tenant data and issuer-key reads; arbitrary auth-row updates |
| mutation function owner (new NOLOGIN) | Minimum domain DML + audit/outbox insert through fixed functions, subject to explicit RLS policies | Superuser/BYPASSRLS/table ownership, key material, role membership exposed to app |
| verifier owner / migration owner | Separate protected function/key read vs controlled DDL responsibilities | Used as request connection |
| outbox worker login (new) | Claim allowed event types; bounded delivery lease/status update, encrypted payload access as required | Grant creation, arbitrary tenant enumeration, raw user-context reuse |

All logins NOINHERIT/NOBYPASSRLS/nonowner. Runtime/provisioner pools must use different actual server login roles: reject pool configuration forcing all users to one privileged server user. SECURITY DEFINER functions have fixed qualified search_path, no caller identifiers/dynamic SQL, explicit EXECUTE grants and PUBLIC revokes. Function owner must be nonowner of domain tables and have explicit RLS policies; FORCE RLS is not an exemption for SECURITY DEFINER. Bind `session_user` to the originating login and `current_user` to the approved function role, never to caller text. Future default function revocation for each creator role must be tested. Exact function signatures/privileges are CR-08-03, not code to copy without review.

## Ordered request flow (recommended READ COMMITTED)

1. Django authenticates server-side session, checks CSRF for unsafe request, normalizes requested action/scope/body and performs coarse authorization. No tenant ORM work in middleware, template rendering or lazy iterators before the transaction.
2. Lease correct role's connection; require idle transaction status, expected login/role flags, approved DB generation and empty context. Unexpected prior context or unknown state: discard/alert, not “reset and hope.” Begin an explicit outermost transaction. Initial proposal: statement timeout <=5s, lock wait <=2s and transaction wall budget <=5s; tune only via reviewed changes.
3. Obtain challenge through pre-context allowlisted interface. Issuer authenticates session/workload and issues context for that challenge and action. On timeout/error: rollback/discard, no domain SQL. Install through the narrow verifier/installer which records the immutable transaction binding and uses parameterized `set_config(..., true)` inside this transaction. Domain RLS and action functions must check the protected binding as well as the signed envelope, so arbitrary SQL cannot replace scope by changing a GUC. The issuer's independently committed first-issuance ledger also prevents obtaining a different valid tuple after rolling back a savepoint that erased the DB binding row; the transactional registry alone cannot provide that guarantee. Session-level SET prohibited.
4. Verification/action gate validates signed bindings. Resolve authoritative guard rows via narrowly privileged functions; lock involved principal rows in ascending UUID order, then actor session row. Shared principal/session locks for operations; conflicting exclusive locks for deactivation/session revoke. Revalidate epochs/active status after locks. No lock upgrades after taking a later-class lock; restart with full lock set if discovery adds an earlier row.
5. For every store-scoped business mutation, lock existing Store authorization guard FOR UPDATE, then idempotency record, then invitations/grants in sorted ID order; recheck actor authority, target status and all versions after acquisition. Reads use a shared Store guard where consistent revocation ordering is required. Every permission-changing route uses the same guard. First provisioning uses a principal-bound provisioning-intent row before newly created Store guard; no existing Store is touched in that path. No client-controlled arbitrary lock scope.
6. Execute one approved logical command, atomically persist effects + business audit + outbox + idempotency result. Commit only while guard checks and deadlines remain valid. Return success only after commit. No external delivery during the transaction.
7. On SQL/validation/timeout/cancel error: rollback whole unit, invalidate local context object, clear ORM/result caches. Return a safe error; never continue a broken transaction. If commit outcome is unknown, return an indeterminate/retryable response; resolve by authoritative idempotency lookup on a fresh authenticated request, not blind re-execution.
8. Before pool return assert idle and context absent with a minimal non-domain diagnostic; if uncertain, close/discard. COMMIT/ROLLBACK is the primary cleanup, not RESET alone. Test role, search_path and context on reuse. A fresh request always obtains new challenge/token even when reusing the same server PID.

The Store guard serializes all authorization-changing operations, including issue/accept/revoke, even when no grant exists. Principal/session guards serialize revocation relative to in-flight operations. A revoker may wait for a prior operation to commit; after revocation commit later gates reject. Token minting before a lock is not sufficient: a changed Store epoch after waiting follows the bounded refresh rule below; changed principal/session epochs remain authorization denials. Avoid cached STABLE verifier results as the only revocation check; the action gate must explicitly lock/re-read authoritative state. Locking across independent identity databases is not assumed; choosing such storage requires another ADR.

## Savepoints, threads, retries and pooling

One actor/scope per outermost transaction. Nested atomic blocks may use savepoints but cannot switch context. Rollback to a savepoint before installation removes context; abort outer unit and reacquire a fresh context rather than silently restore stale authority. Every effective scoped authorization mutation (membership/grant/owner change or invitation issue/accept/cancel/revoke) increments `authz_epoch` atomically; no-op retries do not. This intentionally invalidates other snapshots in that Store. After acquiring guards, verify signature/session/principal/MFA and current actor capability first. If those remain valid but only the signed Store epoch is stale, return internal `AUTHZ_SNAPSHOT_STALE` (proposed SQLSTATE PZ001) before any business effect. This is distinct from 42501, not exposed as a permission oracle to the browser. The adapter rolls back, reauthenticates the same active session and current scope, obtains a new challenge/token and retries the same command/key/body. A revoked actor/session, invalid signature, stale MFA or terminal invalid invitation is not repaired this way.

Transaction retries (propose max 3 total attempts shared across 40001, 40P01 and authenticated Store-snapshot refresh) get a new transaction/challenge/token, reauthorize and reuse the same idempotency key/body. Log every attempt; no retry for 42501, missing MFA or cryptographically invalid token. Exhaustion returns a safe retryable conflict with no uncommitted effects, not success. Lock timeouts remain visible; no infinite retries.

No shared connection across threads/tasks or async context variables reused between requests. No streaming tenant query after transaction exit. Background tasks begin their own authorized transaction; outbox carries an event reference, not a bearer user context. `on_commit` may wake a dispatcher but is not durable delivery.

Initial mode: direct connections, then session pooling. Transaction pooling may be admitted only after pinned PgBouncer/driver tests prove BEGIN pins the server connection, tx/PID obtained on that connection, parameterized transaction-local context clears on reuse, and no reliance on session SET/search_path/temporary state/prepared SQL plans remains. Fully qualify objects. Statement pooling is rejected because the contract needs multi-statement transactions. No current PgBouncer version/configuration is approved in this mission.
